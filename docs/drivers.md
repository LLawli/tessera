# Drivers

## How the drivers reach Tessera

Tessera's own package carries one driver, [OpenSC](#opensc), free software and built in. The vendors' drivers are not part of it: their licenses do not allow redistributing them, and each user needs only the one for their token. Each is a **Flatpak extension** of Tessera, installed by hand:

| Extension | For | Vendor files (sha256) |
|---|---|---|
| `io.github.pedrohqb.Tessera.Driver.SafeSign` | GD Burti (G+D StarSign) and other SafeSign tokens | SafeSign IC 4.5.0.0 `SafeSignICStandardLinux4.5.0.0-AET.000ub2404x86_64.deb` (`7742e21e…1b91`) and, for Token Administration, `…redhat10x86_64.rpm` (`2f5ea462…3378`); GDBM from Ubuntu 24.04, `libgdbm6t64_1.23-5.1build1_amd64.deb` (`18d6d74a…645e`) and `libgdbm-compat4t64_1.23-5.1build1_amd64.deb` (`fb8564af…ee65`) |
| `io.github.pedrohqb.Tessera.Driver.SafeNet` | SafeNet eToken 5100/5110, IDPrime cards | SafeNet Authentication Client 10.9.6885, `GlobalSign-SAC-Linux-Ubuntu-24.04.4-v10.9.zip` from GlobalSign (`c076c2ec…f428`) |
| `io.github.pedrohqb.Tessera.Driver.SerproID` | Serpro's cloud certificate | `SerproID-2.1.6-amd64.deb` (`0ffa9ffe…e588`) |
| `io.github.pedrohqb.Tessera.Driver.ePass2003` | Feitian ePass2003, as certificate authorities deliver it | Feitian's EnterSafe Castle SDK for Linux of 2014-11-28, `ePass2003_Castle_20141128.tar.gz` from Soluti (`00fbb575…0a23`); only `libcastle.so.1.0.0` (x86_64) is kept ([below](#epass2003-feitian)) |
| `io.github.pedrohqb.Tessera.Driver.RemoteID` | Certisign's RemoteID cloud certificate | RemoteID's own release build, from its GitHub releases; packaged and pinned on FlatPark by RemoteID's developer ([below](#remoteid)) |

```bash
flatpak install flatpark io.github.pedrohqb.Tessera.Driver.SafeSign
```

After installing one, quit Tessera from its menu and open it again: Flatpak mounts extensions when the app starts.

The browser plugins Web PKI and WebSigner are extensions too, of another extension point: see [Web signers](signers.md).

- **The extension point** is in Tessera's manifest: `io.github.pedrohqb.Tessera.Driver`, directory `lib/tessera/extensions`, with `subdirectories`, `no-autodownload` and `autodelete`. Each extension is mounted at `/app/lib/tessera/extensions/<Name>` (`SafeSign` for `…Driver.SafeSign`), where Tessera looks for a `driver.toml`. The driver's id is the folder's name in lowercase (`safesign`). Nothing is installed with Tessera on its own: the user picks the driver, and third parties publish theirs the same way (Certisign's RemoteID, by its own developer, is one).
- **What an extension holds** (`flatpak/extensions/<Name>/`): its manifest (`build-extension`, with Tessera as its `runtime`, branch `stable`), the vendor's files as *extra-data*, `apply_extra.sh`, `driver.toml`, an AppStream `addon` component and its icon. It has no permissions of its own: it runs in Tessera's sandbox with Tessera's.
- **Extra-data:** at install time, Flatpak downloads each file from the vendor's site, checks the pinned sha256, and only then runs the extension's `apply_extra.sh`, without network, in the extension's `extra/` folder. The sha256 values are the same as in [distrobox-adv-br](https://github.com/pedrohqb/distrobox-adv-br). Flatpak also requires each file's size; `scripts/pin-drivers.py` downloads each one, checks the sha256 and fills in the size. Continuous integration runs it before every build, then builds each extension and installs it, so `apply_extra.sh` runs on the real downloads and the module it should leave is checked. A weekly workflow checks the pins again.
- **Each driver separately:** a vendor that changes or removes a file breaks only its own extension, and a new vendor version is a new version of that extension alone.
- **An extension holds all of Tessera's permissions.** Whatever runs inside Tessera, a driver included, can write `~/.config/pkcs11/` (the modules the host's p11-kit loads) and the NSS databases of the apps Tessera sets up, so it can choose what host processes load. That is inherent to what Tessera does. So an extension, by the vendor or by a third party, deserves the same trust as Tessera itself: install only the ones you need, from a source you trust, and expect them (on FlatPark, they are) to be reviewed as an app with all of Tessera's permissions. FlatPark's reviewer pointed this out on the 0.3.0 review.

### Which one to install

The window lists the drivers that are not installed (RemoteID marked **Experimental**), each with a button to its FlatPark page (whose install button hands it to the app store, where it is also an add-on on Tessera's page) and one that copies the install command. When a token is connected and its driver is missing, its reader says which one: the reader's name (a USB token is its own reader, named after its product: "SafeNet eToken 5100", "StarSign CUT S") or bytes of the card's ATR (IDPrime's `80 31 80 65 B0`, the eToken Java cards' `80 73 C8 21 10`, the G+D Sm@rtCafé Expert 6 and 7 of the StarSign tokens, `SCE6`/`SCE7`) point to SafeNet or SafeSign (`src/catalog.rs`). The ePass2003's reader is not used for a suggestion: an ePass2003 formatted by OpenSC needs no extension. The command uses the installation Tessera is in (`--user` or `--system`, from `/.flatpak-info`). The rules are few on purpose: a wrong guess only shows a suggestion. Nothing is suggested while a running driver serves a token in that reader (by the slot's description, which OpenSC and SafeNet name after the reader): an IDPrime card that the built-in OpenSC serves needs no SafeNet. `tessera status` prints the readers' ATRs and the same suggestions.

## The "clean" unpacking

Each `apply_extra.sh` follows the same "cleanups" as distrobox-adv-br:

- only the package's files are extracted (the `.deb`'s `data.tar`, read with `bsdtar`, because the runtime has neither `dpkg` nor `ar`);
- **no vendor script runs** (no `postinst`/`postrm`);
- the package's `/etc` is discarded;
- everything goes in the extension's `extra/` folder, and nothing is written outside it; links inside it are relative, and the launchers name its final place, `/app/lib/tessera/extensions/<Name>/extra`;
- a driver that cannot be unpacked fails its own installation, with the reason in the output; a missing optional tool (SafeSign's Token Administration, the SerproID app) is only logged.

An excerpt from SerproID's `driver.toml` (paths relative to the extension's folder):

```toml
name = "SerproID"
vendor = "Serpro"
description = "Cloud certificate; sign in with the SerproID app"
module = "extra/libserproidp11.so"
library_path = ["extra/usr/lib"]                         # the driver's LD_LIBRARY_PATH
create_dirs = ["~/.config/serproid/certificados"]        # created before starting

[env]                                                    # environment of the driver's server
LD_PRELOAD = "libgcc_s.so.1"
XDG_CONFIG_HOME = "~/.config"
SSL_CERT_FILE = "/etc/ssl/certs/ca-certificates.crt"
SSL_CERT_DIR = "/etc/ssl/certs"

[[tools]]                                                # buttons in the window
name = "SerproID"
exec = ["extra/serproid"]
```

A driver that talks to its token over USB itself, not through pcscd, also says `usb = true` (served by one process for every app, held back until Tessera can reach the USB devices) and, for its reader, `pcscd_ignore = "<reader name>"` (held back while pcscd lists it). `usb_id = "vvvv:pppp"` names the token, so that Tessera can offer to undo that setup once the driver is off ([the two formats](#the-two-formats-of-the-epass2003)). The ePass2003's is the one so far ([below](#epass2003-feitian)).

`shared = true` has a driver served by one process for every app, as the `usb` ones are, without their setup (OpenSC's). `patient = true` gives a driver's listing a minute instead of ten seconds, for cards read slowly (OpenSC's; a driver with `usb = true` has it already).

### Icons

The extensions' icons, shown in FlatPark's catalog, come from the vendors where they publish one: SafeSign's is Token Administration's own (256 px, from its package), SerproID's is the official one from Serpro's [integration manual](https://neoid.estaleiro.serpro.gov.br/documentacao/suporte/icones-logomarcas-integracao/). SafeNet's Linux package only has a 32 px badge, so its extension has an icon of its own, a generic USB token in Tessera's colors, without the vendor's mark. Feitian's Linux package has no image at all, so the ePass2003's has one of its own too: a slim token with a swivel cover, in Tessera's colors turned around (gold body, bronze trim), so it does not look like SafeNet's.

## SafeSign IC (GD Burti)

- **Library:** `libaetpkss.so`, linked at `extra/libaetpkss.so`.
- **GDBM:** the library needs `libgdbm_compat.so.4`, which the GNOME runtime does not have. The symptom was the driver not loading. The two Ubuntu 24.04 GDBM packages go to `extra/gdbm`, which is part of `library_path`. The AUR package (`safesignidentityclient`) also depends on `gdbm`.
- **Token Administration:** the `tokenadmin` from the Ubuntu `.deb` needs wxWidgets, which the runtime does not have. The one from the RHEL 10 RPM does not, and that is the one Tessera uses, like the AUR. It runs through a launcher (`extra/tokenadmin`) that puts the SafeSign libraries and GDBM on `LD_LIBRARY_PATH`. It needs full X11 (`--socket=x11`).
- **The registry and `jcdata.kit`:** SafeSign reads a `registry` file that names its data files by where the package installs them (`"UNIXJCDataFilePath"="/usr/share/safesign/jcdata.kit"`), a folder Tessera's sandbox does not have. It looks for that file in `$HOME/.safesign/registry` before `/usr/share/safesign/registry`. `apply_extra.sh` writes a copy with the paths pointing into the extension (`extra/home/.safesign/registry`; the vendor's file is untouched), and `driver.toml` sets `HOME = "./extra/home"` for the driver's process. Only that process gets it: Tessera, the apps and Token Administration keep their own. The folder is read-only, like the rest of the extension.
- **Two GD Burti models.** The older "StarSign Crypto USB Token" (ATR `3B FD 18 00 00 81 31 FE 45 53 43 45 36 30 2D 43 43 30 38 31 2D 46 C2`, "SCE60-CC081") needs `jcdata.kit` to sign: without it the token lists its certificates and takes the PIN, and every `C_Sign` fails with `CKR_DEVICE_ERROR`. The newer "StarSign CUT S" (ATR `3B F9 96 00 00 81 31 FE 45 53 43 45 37 20 0E 00 20 20 28`) signs without the file, which is why the missing path went unnoticed until November 18 ([History](history.md) item 68).
- **Observed behavior:** with the token connected, the first object search (`C_FindObjectsInit`) takes about 1.6 s. The OAB token has 4 certificates (the three CAs of the chain and the holder's). The driver advertises PSS with SHA-1/256/384/512, in addition to PKCS#1 v1.5.

## SafeNet Authentication Client (eToken 5100/5110, IDPrime)

- **The download.** GlobalSign, a certificate authority that ships these tokens with its certificates, distributes Thales's Linux release for Ubuntu 24.04 as a 22 MB zip, with the full package and the "withoutUI" core one, each with Thales's PGP signature (key `B37EBA84D2EB0C786F91EEF77F8AA801285DEE57`, checked when the zip was pinned); the AUR's `sac-core` uses the same zip. Until November 2026 the extension took DigiCert's `Linux_SAC_10.9_GA.zip`, 91 MB with packages for several distributions, and version 10.9.4723. As in distrobox-adv-br, only the core package is used (`…safenetauthenticationclient-core_*_amd64.deb`, about 1 MB). The zip's folders are read-only (0555), so `apply_extra.sh` makes them writable before removing them.
- **Library:** `libeToken.so`.
- **Observed behavior:** with no token connected, the driver was slow to respond in the first test, and the system's p11-kit, when loading it, made Firefox show "Unable to add module". That is why supervision exists: a driver that does not respond is not published. Each driver can also be turned off in the window. With a real SafeNet token, a user on Arch Linux reported it working in PJeOffice Pro when it was still built into Tessera ([compatibility](compatibility.md)); as an extension, it has not been tried with a token yet, in either version (10.9.4723 from DigiCert's zip, or 10.9.6885 from GlobalSign's).

## OpenSC

[OpenSC](https://github.com/OpenSC/OpenSC) is the free PKCS#11 driver for smart cards and tokens: PIV cards and YubiKeys, OpenPGP cards, CardOS, Gemalto IDPrime, SmartCard-HSM, MyEID, several national ID cards and others (the list is OpenSC's `internal_card_drivers`, in `src/libopensc/ctx.c`). All of it is served. The window names the Feitian ePass2003 under OpenSC as "in the free format (formatted by OpenSC)": OpenSC reads only the ePass2003 it formats itself (PKCS#15), and the ones certificate authorities deliver need [Feitian's library](#epass2003-feitian). One token is in one format or the other, and one machine serves one of them at a time ([below](#the-two-formats-of-the-epass2003)).

- **Built in, not downloaded.** OpenSC is LGPL 2.1, so the manifest builds it from the release tarball (0.27.1, pinned by sha256), right after pcsc-lite, which it uses to reach the readers. OpenSSL and secure messaging are required (`--enable-openssl --enable-sm`), so the build fails rather than leave out the drivers that need them. Its `opensc.module` for p11-kit would go to the SDK's read-only `/usr`; it is sent to `/app/share/p11-kit` and cleaned up, since Tessera publishes the module its own way. Its files are in Tessera's `/app` tree: `opensc-pkcs11.so` and `libopensc.so` in `/app/lib`, the command-line tools in `/app/bin` (used by `tessera opensc`). The static library is not built (`--disable-static`). They also go in the release tarball, so FlatPark's package (which unpacks that tree to `/app/extra/tessera`) has them too. `pkcs11-register`, which adds OpenSC to the browsers' NSS databases by itself, is left out.
- **`driver.toml`** names the module by a path relative to its own folder (`../../../opensc-pkcs11.so`), which resolves to `/app/lib/opensc-pkcs11.so` in Tessera's Flatpak and to `/app/extra/tessera/lib/opensc-pkcs11.so` in FlatPark's. A leading `./` in an `env` value is the driver's folder too.
- **Configuration.** `OPENSC_CONF` points at `flatpak/drivers/opensc/opensc.conf`, installed next to `driver.toml`, so OpenSC never reads `/app/etc` (which FlatPark's package does not have). It keeps OpenSC's defaults but one: `use_file_caching = public`, which OpenSC turns on by itself only for a few cards. Certificates and the other public files of a card are then kept in the sandbox's `~/.var/app/io.github.pedrohqb.Tessera/cache/opensc` and read from there the next time; keys and PINs are never cached. An ePass2003 with five certificates took 18.7 s to read and 2.7 s from the cache. If a card's contents are changed elsewhere and Tessera still shows the old ones, delete that folder.
- **One process for every app.** `driver.toml` says `shared = true`: OpenSC is served by `tessera shared` ([architecture](architecture.md)), loaded once, not by a process per connection. With the ePass2003 in the free format, Firefox, the window's two listings and `tessera status` were six processes, each opening the card anew and waiting for the others: Firefox hung and the listing ran out of time, though a signature did get through. One process reads the card once. What comes with it: one call at a time for all of OpenSC's cards, and the login belongs to the process, so a PIN typed in one app leaves the token open to the others until one logs out or the token is unplugged (as with any driver loaded once, the ePass2003's included). Checked with the system's OpenSC and no reader (served, no slot, listed at once), with SoftHSM in the tests, and with the real token: Firefox no longer hangs.
- **The encrypt flag, for Java.** OpenSC reports `CKM_RSA_PKCS` and `CKM_RSA_X_509` as sign, verify and decrypt, without encrypt (`register_mechanisms`, `framework-pkcs15.c`). Java's SunPKCS11 drops a mechanism that decrypts and does not encrypt, signing included ([JDK-8176837](https://bugs.openjdk.org/browse/JDK-8176837); later versions check per use or have `allowLegacy`, [JDK-8293345](https://bugs.openjdk.org/browse/JDK-8293345)). PJeOffice signs with `NONEwithRSA`, which is `CKM_RSA_PKCS`: Java went on to BouncyCastle, which cannot use a token's key, and PJeOffice showed "Supplied key (sun.security.pkcs11.P11Key$P11PrivateKey) is not a RSAPrivateKey instance". The trace had the login and the keys read, and no `C_SignInit`. `driver.toml` sets `TESSERA_ENCRYPT_FLAG = "1"`: Tessera adds `CKF_ENCRYPT` to what `C_GetMechanismInfo` reports for the mechanisms that decrypt (`src/mechflags.rs`). The flag is not true (`C_EncryptInit` still fails in OpenSC); apps encrypt with a public key in software. With it, PJeOffice signed with the ePass2003 in the free format.
- **A minute to list.** `driver.toml` says `patient = true`: the listing of OpenSC's tokens gets 60 s instead of 10 s (`status.rs`), as the drivers with `usb = true` do. Without it, that first read of the ePass2003 ran out of time ("No answer; trying again") and, after three tries, supervision stopped the driver.
- **SafeNet's cards.** OpenSC's `idprime` driver knows the cards SafeNet's driver serves (IDPrime, eToken 5110). With both on, the same token would show twice. `driver.toml` has a `[when_on.safenet.env]` section: while SafeNet's server runs, `OPENSC_CONF` is `opensc-without-idprime.conf`, which lists every OpenSC card driver but `idprime`. Switch SafeNet off, or let it fail or be stopped by supervision, and OpenSC is started again with every driver and serves those cards (`settle` in `server.rs`); when SafeNet comes back, OpenSC is started again without `idprime`. The list follows OpenSC's; it must be checked when OpenSC is updated. Whether OpenSC's `starcos` or `cardos` drivers also claim some SafeSign or SafeNet tokens is not known yet; the duplicate warning below would show it, and the same kind of section would fix it.
- **GD Burti's tokens are left alone.** OpenSC has no driver for the G+D StarSign CUT S (one is proposed, [PR #3764](https://github.com/OpenSC/OpenSC/pull/3764), not merged). Without one, it probes the token with its card drivers' selects and polls its status, and the token hangs: SafeSign then cannot use it either. It was seen on Fedora with the system's OpenSC, and again with Tessera's: with OpenSC switched off in the window, the token worked through SafeSign at once. Both configurations have `ignored_readers = "StarSign"`: a reader whose name holds that text (the token is its own reader, "… StarSign CUT S …") is never opened by OpenSC. A G+D card in an ordinary reader is not covered (OpenSC ignores by reader name only); for it, switch OpenSC off in the window.
- **The system's OpenSC is switched off.** Fedora and Bluefin ship OpenSC registered with p11-kit, and the system's OpenSC has no `ignored_readers`: whenever anything opened the GD Burti's token through p11-kit, it hung the token, and GNOME's session with it (the login waited on it), and it showed every other OpenSC card twice. So, from its first start, Tessera writes `opensc.module` and `opensc-pkcs11.module` (Debian's and Ubuntu's name) in `~/.config/pkcs11/modules`, each with `enable-in: tessera-turned-it-off`, a program that does not exist. p11-kit reads the user's module files first and takes from the system's file of the same name only what the user's does not set (`_p11_conf_load_modules`, `p11-kit/conf.c`), so the system's OpenSC is off for `p11-kit-proxy.so` in native apps and for the system's p11-kit server, without touching the system's file; a file for a module the system does not have does nothing. The files stay with Tessera closed, which is the point: the token must not hang before Tessera starts. The switch **Switch off the system's OpenSC**, in the window's Service section, removes them (kept in `settings.toml` as `system_opensc_on`); Tessera only changes or removes files that start with its own first line, so a user's own `opensc.module` is left as it is. The change reaches each program the next time it loads its modules: at once for new apps and for each new connection to the system's server (which runs `p11-kit remote` per connection), at their next start for apps already open. Uninstalling Tessera leaves the files (the FAQ says how to remove them). The window's warning about tokens seen twice stays for other cases (a vendor driver installed on the system as well as Tessera's extension), and for systems whose p11-kit ignores the user's configuration (`user-config: none` in `/etc/pkcs11/pkcs11.conf`).
- **Duplicates in general.** A token two of Tessera's drivers serve (found by the holder's certificate, issuer and serial number, not the CA chain both may carry) gets a warning in the window and in `tessera status`. So does a token the apps see more often through the system's p11-kit server than Tessera serves it: the system has a driver of its own for it, for example a SafeNet client installed on the system as well as Tessera's extension. Then one of the two should go. The system's OpenSC no longer causes this (above).
- **No slots.** With no reader connected (a USB token is its own reader, so unplugged means none), OpenSC lists no slot at all. The `cryptoki` crate then asks again with an empty buffer, and through p11-kit's RPC that answers `CKR_BUFFER_TOO_SMALL`, which it retried without end: the listing hung until its time limit and supervision would have stopped the driver. Tessera now asks for the count first (`status.rs`, `slot_count`), for its own servers only: through `p11-kit-client.so` the count takes a second connection, so a second load of the driver, and the system's server always has slots (its trust store). No other driver had shown it, because they all keep at least one slot.
- **Tools.** OpenSC has no windowed tools; the command-line ones (a fixed list, OpenSC's own) run with `flatpak run io.github.pedrohqb.Tessera opensc TOOL [ARGS]` (`pkcs15-tool --change-pin`, `--unblock-pin`, `--list-certificates`, `opensc-tool --list-readers`, `pkcs11-tool --list-slots`…), with the driver's configuration; `pkcs11-tool` gets the module unless `--module` is given. `pkcs15-init`, which initializes blank cards, reads its profiles from `/app/share/opensc`, a path fixed at build time: in FlatPark's package, where Tessera's tree is under `/app/extra/tessera`, it does not find them. Changing and unblocking the PIN (`pkcs15-tool`) need no profiles.
- **Debugging.** `flatpak run --env=OPENSC_DEBUG=3 io.github.pedrohqb.Tessera`: OpenSC writes its log to standard error, which goes to the driver's log (`data/tessera/logs/opensc.log` in Tessera's folder).
- **ePass2003 formatted by Feitian's software.** The first real ePass2003 tried (November 2026), issued by a certificate authority, was recognized by OpenSC (its `epass2003` driver) but not read: "PKCS#15 binding failed: Unsupported card". OpenSC reads the ePass2003 it formats itself (PKCS#15); Feitian's middleware writes a format of its own (ENTERSAFE-ESPK). Feitian's own library reads it: see [ePass2003 (Feitian)](#epass2003-feitian).
- **ePass2003 formatted by OpenSC.** A blank ePass2003 (in FIPS mode) was formatted with `pkcs15-init` and got A1 certificates (November 2026; three with their keys by now, and their chain). The token's ATR changes with its state: it ends in `00:00:00:13` while blank and is `3b:9f:95:81:31:fe:9f:00:66:46:53:05:01:00:11:71:df:00:00:03:90:00:80` once initialized, the same model both times. An unpatched OpenSC 0.27.1 reads such a token and signs with it. Writing to it (formatting, importing a key) fails on 0.27: the `epass2003` driver selects the current folder again and the card answers `6982`, and the secure messaging session is lost when another process renews it (`6988`). Both are fixed upstream, by [#3892](https://github.com/OpenSC/OpenSC/pull/3892) and [#3921](https://github.com/OpenSC/OpenSC/pull/3921), merged into OpenSC's `master` on November 18, 2026 and in no release yet; the token was written with an OpenSC built from 0.27.1 plus those two, and the results were reported on both. Tessera's OpenSC is the 0.27.1 release, so it uses such a token but does not format one; when a release carries the two fixes, the manifest's OpenSC is to be updated. Through Tessera the token is listed with its certificates and passes Serpro's client certificate test in Firefox (the cache, the longer limit and the one process above came from that test), and PJeOffice signs with it (the encrypt flag above).
- **Not yet tested with any other real token.** Checked besides: the configuration files (`opensc-tool -D` with each one, against OpenSC 0.25), and the driver served by `tessera serve` with no reader, listed and published.

## ePass2003 (Feitian)

Feitian's ePass2003 is the token several Brazilian certificate authorities deliver (Soluti among them), formatted by Feitian's software. OpenSC does not read that format ([above](#opensc)); Feitian's own PKCS#11 library does. It works with a real token (November 2026): listed, Firefox and Brave (Flatpak) passed Serpro's client certificate test (`ccd.serpro.gov.br/testeaqui`, TLS 1.3), and PJeOffice Pro (Flatpak) signed with Firefox open on the same token.

- **The download.** Soluti's installation guide links Feitian's EnterSafe Castle SDK for Linux of 2014-11-28 (`site.solutinet.com.br/drivers/Token/ePass2003/Linux/ePass2003_Castle_20141128.tar.gz`, 9 MB). `apply_extra.sh` keeps only the 64-bit PKCS#11 library, `x86_64/redist/libcastle.so.1.0.0`, which needs nothing beyond glibc and libstdc++; the samples, the GTK 2 PIN manager, the Firefox and Thunderbird scripts and `config.sh` (which would open the token's USB device to every user) are left out. The 2018 version of the SDK behaved the same in testing, and Hypersecu's `libcastle_v2` (for its HYP2003) also talks to USB itself; neither was taken. Soluti's link for "Epass Linux Debian - Ubuntu" points to Oberthur's AWP middleware instead, which supports only Oberthur's cards.
- **It talks to the token over USB itself**, not through pcscd, so it needs two things the other drivers do not, declared in its `driver.toml` (`usb = true`, `pcscd_ignore = "Feitian ePass2003"`) and checked by `src/setup.rs`:
  - **The USB devices.** Tessera's sandbox has no `/dev/bus/usb`. The window shows the command that gives it to Tessera alone, `flatpak override --user --device=usb io.github.pedrohqb.Tessera` (`--device=all` with Flatpak older than 1.15.11, which has no `usb`; the version is read from `/.flatpak-info`). It is not in Tessera's manifest: only this driver needs it.
  - **pcscd must leave the token alone.** With pcscd holding the token as a CCID reader, the library's own USB access collided with it: the library hung (in `futex`) and the token stopped answering (`usbfs: … did not claim interface`, `error -71`) until it was unplugged, sometimes until a reboot. pcscd skips the readers named in `PCSCLITE_FILTER_IGNORE_READER_NAMES` (a substring match), so the window shows a command that writes a systemd drop-in, `/etc/systemd/system/pcscd.service.d/tessera-ignore-feitian-epass2003.conf`, reloads systemd and stops pcscd (its socket starts it again, with the setting; the warning that the socket is still active is expected). The command to undo it is in the row's tooltip. It needs `sudo`; Tessera does not run it.
  - Until both are done, Tessera does not start the driver: its row says it waits for the one-time setup, and a row with each command shows below it (`gate` in `src/ui/supervise.rs`, which reads pcscd's readers before each listing). Once done, the rows go away and the driver starts by itself.
- **One process for every app** (`tessera shared`, `src/shared.rs`). The library reads the whole token on its first `C_GetTokenInfo`: 11 s with the real token, 0.26 s after that in the same process. p11-kit server starts a process per connection, each loading the library anew, so each listing paid the 11 s twice (the slot count takes a connection of its own), ran past its 10 s limit, and was stopped in the middle of a USB transfer, which hung the token; and two apps would have been two processes on the same USB device. A driver with `usb = true` is served instead by one process that loads and initializes it once, reads the token once at start (the "warm-up" lines in its log, with timings), and serves each connection on its own thread through `p11_kit_remote_serve_tokens`. Its function list takes `C_Initialize` and `C_Finalize` per connection (the library stays initialized), keeps each connection's sessions apart (`C_CloseAllSessions` and the end of a connection close only that connection's), and lets one call at a time into the library. Its listing may take 60 s, since giving up on it ends only the listing's process. The login state is the library's, so it is shared: once one app has entered the PIN, another finds the token logged in while a session is open, and one app's logout logs out all.
- **RSA-PSS is made by Tessera** (`src/pss.rs`, `TESSERA_PSS_VIA_RAW = "1"` in `driver.toml`). The library lists `CKM_RSA_PKCS_PSS`, but its `C_SignInit` fails with `CKR_GENERAL_ERROR`; TLS 1.3 signs with PSS, so Firefox's handshake failed after the PIN (`SSL_ERROR_HANDSHAKE_FAILED`). Its raw RSA is right: a block padded by hand for PKCS#1 v1.5 and signed with `CKM_RSA_X_509` gave the same bytes as `CKM_RSA_PKCS`. So, as OpenSC does for cards without PSS, Tessera encodes the hash (EMSA-PSS: random salt, MGF1; RFC 8017) and has the token do only the raw RSA operation; the key stays in the token. Only the single-part `CKM_RSA_PKCS_PSS` is taken over. PKCS#1 v1.5 (TLS 1.2, PJeOffice) goes to the library as it is.
- **Other observed behavior:** `C_Initialize` takes 0.8 s; a PKCS#1 v1.5 signature about 0.9 s. `C_DigestInit` fails, which does not matter: apps compute the hash. The administrator PIN (PUK) logs in only in a read-write session (`pkcs11-tool --session-rw --login --login-type so`; read-only gives `CKR_SESSION_READ_ONLY_EXISTS` before the PIN is checked), and `C_SetPIN` in that session fails with `CKR_GENERAL_ERROR`, so the PUK is checked on Linux and changed with Feitian's administrator manager on Windows ([FAQ](../FAQ.md#how-do-i-check-or-change-the-epass2003s-puk)). A process killed in the middle of a USB transfer left threads stuck in USB I/O and the token hung; supervision still stops the driver's process after three listings with no answer, so a hang is still possible, but a slow listing alone no longer causes one.
- **Log:** `~/.var/app/io.github.pedrohqb.Tessera/data/tessera/logs/epass2003.log`.

### The two formats of the ePass2003

An ePass2003 is either in Feitian's format (as certificate authorities deliver it; this extension) or in the free one (formatted by OpenSC, PKCS#15; the built-in [OpenSC](#opensc) driver). The two need opposite things from pcscd: Feitian's library needs pcscd to skip the token, and OpenSC reaches it only through pcscd. The filter is by reader name, and both tokens are "Feitian ePass2003", so one machine serves one format at a time.

To go from Feitian's format to the free one: switch the ePass2003 (Feitian) driver off and OpenSC on. While that driver is off and something of its setup is left, the **Drivers** page shows rows under it, each with a command to copy (Tessera runs nothing itself):

- **Undo the setup: the card service.** With the token plugged in, Tessera knows: the row says the setup is still in place when pcscd does not list the reader, and goes away when it does. The token is recognized by the `usb_id = "096e:0807"` of the extension's `driver.toml`, or, for the extension's first release, which did not have it, by the same id in Tessera's own list (`catalog.rs`); it is looked up in `/sys/bus/usb/devices`, which the sandbox reads without the USB permission. With the token unplugged Tessera cannot tell (the drop-in is in `/etc`, which the sandbox does not see), and the row is shown all the same, saying "if you did its one-time setup": the command is never missing (`setup::pcscd_left`). The command removes the drop-in and restarts pcscd (`setup::pcscd_undo_command`).
- **Undo the setup: USB**, when Tessera still reaches the USB devices: `flatpak override --user --nodevice=usb io.github.pedrohqb.Tessera` (before Flatpak 1.15.11, where the grant was `--device=all`, `flatpak override --user --reset io.github.pedrohqb.Tessera`, which also drops any other override of Tessera's). It shows after a restart of Tessera at the earliest, and goes after the next one.

Switching the driver on again asks for the one-time setup again (`setup::leftover`, `setup::unmet`).

## SerproID

SerproID is a cloud certificate. The driver (`libserproidp11.so`) does not talk to any reader: it reads the list of certificates downloaded by the SerproID app and, for each signature, asks for approval on the holder's phone through Serpro's cloud. It was the hardest driver. All the quirks below were found in testing, and most of them do not show up when the driver is loaded directly by an application (like Firefox in the distrobox).

### Configuration it requires

1. **The certificates folder must exist,** even if empty: `~/.config/serproid/certificados`. Without it, the SerproID app closes. distrobox-adv-br does the same. Tessera creates it (`create_dirs`) before starting the driver and before opening the app.
2. **The configuration folder:** the driver reads `serproid/certificados` and `serproid/ambiente` and writes `serproid/serproid.log` in the user's configuration folder. Flatpak sets `XDG_CONFIG_HOME` to the app's own configuration folder, so the driver and the app would look in different places. `driver.toml` sets `XDG_CONFIG_HOME=~/.config`, and the manifest has `--persist=.config/serproid`, which keeps that folder in `~/.var/app/io.github.pedrohqb.Tessera/.config/serproid`.
3. **CA certificates:** the bundled OpenSSL looks for the roots in `/usr/lib/ssl`, the Debian location, which the runtime does not have. `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` and `SSL_CERT_DIR=/etc/ssl/certs`.
4. **The app:** the startup script and the app's configuration use absolute paths (`cd /usr/share/serproid-desktop; ./jre/bin/java …`). `apply_extra.sh` replaces these paths, only in the text files, with the copy in `/app/lib/tessera/extensions/SerproID/extra`. The app is JavaFX and only draws through X11 (the error was `Unable to open DISPLAY`).
5. **`libneoidp11.so`:** the module is also offered under this name, as in distrobox-adv-br, because some signers look for it that way.

### The four quirks that break signing

1. **`undefined symbol: _Unwind_Resume_or_Rethrow`.** The library uses the exception unwinder from `libgcc_s` without declaring it as a dependency. In a C++ or Java application, `libgcc_s` is already loaded, and the error does not appear. In `p11-kit-remote` (in C) or in Tessera (in Rust), `dlopen` fails and p11-kit only returns `CKR_DEVICE_ERROR`. The fix is `LD_PRELOAD=libgcc_s.so.1` in the driver's environment. The real error only showed up with `P11_KIT_DEBUG` on a server started by hand.
2. **It keeps the mechanism pointer.** In `C_SignInit`, PKCS#11 only guarantees that the `CK_MECHANISM` (and the PSS parameters) is valid during the call. SerproID keeps the pointer and only reads the parameters in `C_Sign`. An application that loads the driver directly keeps the parameters alive, and everything works. Through p11-kit, they live in the RPC message, which is reused as soon as `C_SignInit` returns. In `C_Sign`, the PSS hash field was corrupted. In a fake driver that reproduces the defect, `0xd963a0444bf2382c` arrived instead of `0x250` (SHA-256). The request went to the cloud with the wrong hash, the phone received the request, the approval gave "Ops! Estamos enfrentando problemas" ("Oops! We are experiencing problems"), and the driver kept retrying until it returned `CKR_FUNCTION_CANCELED` (`Retornando CKR_FUNCTION_CANCELED depois de receber 20 vezes AGUARDANDO.` in the log). The proof was `sign-test.py clobber`: with the parameters wiped right after `C_SignInit`, the direct driver failed immediately. The fix (`src/stable.rs`) is for `tessera remote` to hand the driver a copy of the mechanism that lasts until the next `*Init` on the same session. It applies to all drivers.
3. **With a size query, it signs in PKCS#1 v1.5.** If `C_Sign` is first called without a buffer (to learn the size, as the `cryptoki` library does), SerproID returns a PKCS#1 v1.5 signature of the data, even when the requested mechanism is PSS. TLS 1.3 requires PSS, and the site responds with `SSL_ERROR_DECRYPT_ERROR_ALERT`. An intermediate attempt, which added the size query to work around item 2, had this effect and was reverted. NSS (Firefox, Papers) calls `C_Sign` only once, with a buffer, which is the right path.
4. **Labels with NUL.** The token fields (label, manufacturer, model, serial) come padded with NUL bytes instead of spaces. Tessera cleans them up when displaying them.

### Its serial number

SerproID's token reports serial `1`, the same as the "System Trust" and "Default Trust" tokens of p11-kit's trust store. Apps that tell tokens apart by serial then take SerproID for one of those. PJeOffice Pro (signer4j) keeps one device per serial: natively it saw SerproID, but in the Flatpak, through the system's p11-kit server, the trust store's slots come first and SerproID was the duplicate it dropped (keytool, through the same `pkcs11.so`, did list its certificate). So `tessera remote` reports serial `SERPROID` for SerproID's tokens (`src/serial.rs`): Tessera sets `TESSERA_TOKEN_SERIAL=SERPROID` in its environment unless the `driver.toml` sets it, and any driver can set it in `[env]`. Only the serial changes; label, model and the certificates are SerproID's own. A JSignPdf set up for SerproID before this asks to be set up again once, since it remembers the token by label and serial.

### Other observed behaviors

- **Mechanisms:** only `CKM_RSA_PKCS` and `CKM_RSA_PKCS_PSS`. There is no `CKM_SHA256_RSA_PKCS` (`Mecanismo invalido: 0x40` in the log). Whoever signs must compute the hash first.
- **Interface:** PKCS#11 2.20, without `C_GetInterface`.
- **Token:** `CKF_PROTECTED_AUTHENTICATION_PATH` and no login. The "password" is the approval on the phone.
- **Application identification:** for each signature, the driver reads `/proc/self/exe` and writes the path to the log. The name appears on the phone as "Aplicação" (Application) ("Tessera", through p11-kit). Testing showed that the name does not matter for approval.
- **Authorization window:** right after an approval on the phone, new signatures from the same application go through without asking, in about 0.2 s, for a few minutes. This confused several tests, because a signature "that worked" may not have gone through approval.
- **Cached signatures:** the same digest signed again returns the same signature, in 0.2 s.
- **Notification:** for each request, it runs `sh -c "notify-send … 'Foi enviado um pedido de PIN para o seu dispositivo.'"`, with an image from its own folder that the desktop outside the sandbox cannot open. Tessera puts its own `notify-send` first on the drivers' `PATH` (in `~/.var/app/io.github.pedrohqb.Tessera/data/tessera/libexec/bin`), which strips the icon and images and shows Tessera's icon. It sends the notification to Flatpak's notification portal itself (`gdbus`), with a new ID each time: libnotify's `notify-send`, in a sandbox, names every notification after a counter that starts at 1 in each process, so each one replaced the previous one, and Plasma (unlike GNOME) only updates a replaced notification in its history. The second request in a row, say when signing several documents, went unannounced. If the portal call fails, it falls back to `notify-send` without the driver's image.
- **Log:** `~/.var/app/io.github.pedrohqb.Tessera/.config/serproid/serproid.log`. The file is appended to, not cleared. Lines like `Tipo de classe nao tratado em C_FindObjectsInit: 0x9` are NSS searches for objects the driver does not have, and do not indicate an error.
- **`maquinaId`:** a file in the same folder identifies the machine in the cloud. Tessera's is different from the distrobox's.

### What was not the cause (and was ruled out in testing)

The program name, the command line, the environment, signals, standard input and output, initialization with `CKF_OS_LOCKING_OK`, the finalize and re-initialize that p11-kit does before each connection, several instances of the driver at the same time, and the age of the connection. Each one was tested individually. The path is in [History](history.md).

## RemoteID

[RemoteID](https://github.com/LLawli/RemoteID-linux) makes a Certisign RemoteID cloud certificate available on Linux as a token. It is an independent open source project (GPL-3.0), by Leonardo Lucas, made by **reverse engineering** Certisign's service, which offers no Linux program; Certisign neither made nor endorses it, and a change in its service may stop it working without notice. It was the first driver extension on FlatPark, published by its developer through Tessera's extension point ([History](history.md), item 41).

- **Not in this repository.** The extension's manifest, `apply_extra.sh` and `driver.toml` are in FlatPark's registry (`registry/io.github.pedrohqb.Tessera.Driver.RemoteID`), kept by RemoteID's developer, and it installs RemoteID's release build from its GitHub releases, unmodified. This repository's CI does not build it, and problems with it go to [RemoteID's issues](https://github.com/LLawli/RemoteID-linux/issues).
- **Library and tool:** `extra/lib/libremoteid.so`; the window's **RemoteID** button (`extra/bin/remoteid`) signs in to the account.
- **How it signs:** the private key stays on Certisign's servers; when the signing session has expired, a window asks for the code from the authenticator app. The driver reaches Certisign's servers through Tessera's network access and has no permissions of its own.
- **TLS 1.2 only for website login:** TLS 1.3 requires an RSA-PSS signature, which Certisign's service does not provide. Signing documents is not affected.
- **Bug reports:** `remoteid diagnostico` packs a log with no password, PIN or authenticator code.
- **Experimental:** the window marks it so, in **Available to install** and once installed: it is new, by a third party, and not yet tested by hand here ([Compatibility](compatibility.md)).

## Bird ID (not packaged)

Soluti's cloud certificate. It is not an extension, and will be made only if someone with a Bird ID certificate asks for it and can test it: without one, nothing here could be checked to sign. What a look at Soluti's Linux package (`utility-birdid` 2.4.4, `birdID-Desktop.deb`, November 2026) showed, for whoever takes it up:

- **Two packages, one difference:** "Linux x64" and "Linux x64 18" differ only in the driver and the helper, built for an older glibc (2.15 instead of 2.34) for Ubuntu 18.04.
- **The driver,** `resources/extraResources/linux/x64/vault-pkcs11.so` (130 KB, needs only libcurl and glibc), talks to Soluti directly over HTTPS (`api.birdid.com.br`; OAuth2 with a password grant, then a "signature_session" with a lifetime), not through the desktop app. Its settings are `~/vault/vault.properties` and `~/vault/vault.bin` (this computer's credentials, encrypted), which the desktop app writes at its first login; the paths inside are absolute.
- **The desktop app** is Electron (about 230 MB installed). It runs the helper, `vault-utility-assistant`, from a fixed `/usr/local/lib` path, as a small HTTP server on `127.0.0.127` (for the app and the browser extension). The helper's `-register`, behind the app's "Registrar o driver", adds a "BIRDID VIRTUAL TOKEN" module to every NSS database it finds under the home folder, browsers set up by Tessera included.
- **Likely shape:** an extension that takes only `vault-pkcs11.so`, with no app, server or registration, and reads a copy of `~/vault` in Tessera's own data folder (one command in the window, the paths in `vault.properties` rewritten). Running the Electron app inside Tessera would need `/usr/local/lib` and its setuid `chrome-sandbox`, neither of which a Flatpak sandbox has.
- **To find out first:** whether the PIN the driver asks for is the code from the Bird ID phone app or a fixed password; whether the driver lists the certificate and signs with the app closed; how long a signing session lasts (the default in the driver is 18000, likely seconds).
